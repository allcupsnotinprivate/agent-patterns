# 04. Workflow-паттерны

Детерминированные пути оркестрации LLM-вызовов из «Building effective agents» (Anthropic). Здесь **путь задан кодом**, а не моделью (левый край оси A). Применять, когда задача декомпозируема и путь предсказуем: это предсказуемо и дешево, ценой гибкости.

Это точка входа перед мультиагентностью: пять паттернов ниже покрывают большинство продакшн-задач без полноценного агента.

## Паттерны группы

| Паттерн              | `id` (папка)           | Суть в одну строку                                                  | Статус      | Карточка |
|----------------------|------------------------|---------------------------------------------------------------------|-------------|:--------:|
| Prompt chaining      | `prompt-chaining`      | Последовательность LLM-вызовов с программными gate-проверками       | established |    ⏳     |
| Routing              | `routing`              | Классификация входа → направление в специализированный обработчик   | established |    ⏳     |
| Parallelization      | `parallelization`      | Sectioning (независимые подзадачи) и voting (консенсус) параллельно | established |    ⏳     |
| Orchestrator-workers | `orchestrator-workers` | Центральный LLM динамически декомпозирует и делегирует worker-ам    | established |    ⏳     |
| Evaluator-optimizer  | `evaluator-optimizer`  | Генератор + независимый оценщик в цикле обратной связи              | established |    ⏳     |

## Порядок чтения

По возрастанию гибкости: **prompt-chaining** → **routing** → **parallelization** → **orchestrator-workers** → **evaluator-optimizer**.

Ключевое различие: в **parallelization** подзадачи **предопределены**, а в **orchestrator-workers** - определяются моделью на лету. Это и есть граница между «жестким» и «динамическим» workflow.

## Когда что

- **Prompt chaining** - задача чисто декомпозируема на фиксированные шаги; торгуем латентность за точность.
- **Routing** - вход бывает разных типов (напр., простые вопросы → дешевая модель, сложные → сильная).
- **Parallelization** - sectioning для независимых подзадач; voting для консенсуса (напр., проверка кода на уязвимости несколькими промптами).
- **Orchestrator-workers** - число и вид подзадач заранее неизвестны (напр., правки во многих файлах).
- **Evaluator-optimizer** - есть четкий критерий качества и измеримое итеративное улучшение (напр., литературный перевод). Критик должен быть **независимым** - это надежнее intrinsic self-correction.

## Связи с другими группами

- Evaluator-optimizer - «продакшн-версия» идеи независимого критика из [группы 01](../01-reasoning/) (в отличие от ненадежной intrinsic self-correction).
- Orchestrator-workers - прямой мост к [супервизорной топологии](../05-multi-agent/) (группа 05): отличие лишь в автономности worker-ов.
